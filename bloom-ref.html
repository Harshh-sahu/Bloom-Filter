Bloom Filter Math

Two parameters determine the whole design: n (expected elements) and p (acceptable false-positive probability). Everything else is derived.

Bit-array size

m = ceil( −n × ln(p) / (ln 2)2 )
m = ceil( −10,000,000 × ln(0.001) / (ln 2)2 ) ≈ 143,775,479 bits ≈ 17.2 MB

Number of hash functions

k = round( (m / n) × ln 2 ) = round( 14.37 × 0.693 ) = 10

Current FPP after t insertions

FPP(t) = (1 − e−k·t/m)k
At full capacity (t = 10M): FPP(10M) ≈ 0.001 — the configured target.

💡
Why no false negatives? A bit is set to 1 on insertion and never cleared. If any of the k bit positions for a key is 0, that key was definitely never inserted — the check exits immediately. False positives occur when the k bits for a different set of keys all happen to be 1. The DB confirms or denies.

API Reference

GET /api/v1/usernames/check?username={username}
Check whether a username is available. Fast path takes < 1 ms (no I/O).
username string · required 3–50 chars, [a-zA-Z0-9._]. Normalized to lowercase.
POST /api/v1/users
Register a user. Inserts to DB, then updates Bloom filter + Redis. Returns 409 on duplicate.
usernamestring · required Same rules as above.
emailstring · optional Valid email format.
POST /api/v1/seed/generate?count={n}
Generate n fake usernames for load testing (max 100k per request). Call 10× for 1M+ entries.
# Check availability (Bloom negative = instant, no DB)
curl "http://localhost:8080/api/v1/usernames/check?username=alice"
# {"username":"alice","available":true,"checkedAt":"2024-..."}

# Register a user
curl -X POST "http://localhost:8080/api/v1/users" \
  -H "Content-Type: application/json" \
  -d '{"username":"alice","email":"alice@example.com"}'

# Seed 1M users for load testing
for i in $(seq 10); do
  curl -sX POST "localhost:8080/api/v1/seed/generate?count=100000"
done

# Run k6 load test
k6 run --vus 100 --duration 30s load-test/k6-script.js

# Prometheus metrics
curl localhost:8080/actuator/prometheus | grep bloom_filter

Instagram-scale considerations

🔀

Shard the filter

At 1B+ users, partition by username hash prefix across Redis cluster nodes. Each shard handles ~100M entries independently.

🔄

Async updates

Publish registrations to Kafka. A consumer updates the shared Redis Bloom (Redisson RBloomFilter). Eventual consistency within < 100 ms.

🗑

Deletion

Standard Bloom filters can't delete. Options: counting Bloom (4× memory), Cuckoo filter, or nightly rebuild from DB (10 min for 1B rows at batch=10k).

🌐

Multi-instance

In-process filters diverge across replicas. Use Redis Bloom (shared bit array, +0.5–1 ms latency) or gossip-protocol sync via Kafka events.

⚠️
Custom strategy thread safety: The CustomBloomFilterStrategy uses java.util.BitSet which is NOT thread-safe. It is provided as an educational implementation only. Production use should always use GuavaBloomFilterStrategy (backed by AtomicLongArray) or a Redis-backed shared filter.
